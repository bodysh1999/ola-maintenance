# نظام إدارة الصيانة العقارية — علا التميز

نظام خدمات ما بعد البيع لشركة تطوير عقاري واحدة: يربط **إدارة الشركة** و**موظف الصيانة** و**الفني/المقاول** و**مالك الوحدة** في دورة واحدة من البلاغ حتى الإنجاز والتقييم.

> مشروع مستقل لشركة واحدة — لا يوجد SaaS، ولا باقات، ولا تسجيل شركات، ولا Super Admin.

**التقنيات:** Next.js 15 (App Router) · TypeScript · Tailwind CSS · Supabase (PostgreSQL + Auth + Storage)

---

## ما الذي تم بناؤه في النسخة الأولى

| الواجهة | المسار | أهم الوظائف |
|---|---|---|
| تسجيل الدخول | `/login` | دخول بالبريد وكلمة المرور، استعادة كلمة المرور، إلزام تغيير كلمة المرور المؤقتة |
| مالك الوحدة | `/owner` | وحداته وصورها والضمانات السارية، الطلبات الحالية والسابقة، زر «طلب صيانة» |
| نموذج الطلب | `/owner/requests/new` | 4 خطوات: الوحدة ← نوع العطل (10 أنواع) ← المكان والوصف والصور/الفيديو ← موعد الزيارة، رقم بلاغ تلقائي |
| متابعة الطلب | `/owner/requests/:id` | شريط المراحل الثماني، موعد الزيارة والفني، المحادثة، الموافقة على عرض السعر، التقييم بالنجوم، إعادة فتح الطلب |
| لوحة الإدارة | `/admin` | 10 مؤشرات، رسوم بيانية (يومي، حسب الحالة، حسب النوع)، ما يحتاج إجراء، أحدث البلاغات |
| صندوق موظف الصيانة | `/admin/inbox` | جديدة/مراجعة، بانتظار الاعتماد، معتمدة بلا فني، قطع غيار، متأخرة |
| جدول البلاغات | `/admin/requests` | بحث وتصفية (حالة، نوع، أولوية، مشروع، تاريخ، متأخرة) وتصدير Excel |
| تفاصيل البلاغ (للموظف) | `/admin/requests/:id` | فحص الضمان الآلي وتعديله، الأولوية، تغيير الحالة، تعيين فني مقترح حسب التخصص، الجدولة وإعادتها، عرض سعر، اعتماد/إرجاع تقرير الفني، ملاحظات داخلية، السجل الزمني |
| المشاريع والوحدات | `/admin/projects`, `/admin/units/:id` | المشاريع والمباني والأدوار والوحدات، ربط المالك وتاريخ التسليم، سجل ضمان مستقل لكل وحدة + باقة ضمان قياسية بضغطة |
| العملاء | `/admin/owners` | تسجيل العملاء، **تفعيل الحساب فقط بعد ربطه بوحدة**، إيقاف/إعادة تفعيل |
| الفريق | `/admin/team` | الفنيون (بتخصصاتهم) والمقاولون وحسابات الإدارة وموظفي الصيانة |
| التقارير | `/admin/reports` | أي فترة: الأنواع، الحالات، أكثر المشاريع أعطالًا، أداء الفنيين، أوقات الاستجابة والإصلاح، تكلفة القطع، رضا العملاء — تصدير Excel وPDF |
| الإعدادات | `/admin/settings` | الاسم والشعار والألوان (تنعكس فورًا على كل الواجهات)، أرقام التواصل، مستويات الخدمة SLA، قنوات الإشعار المستقبلية |
| الفني (للجوال) | `/tech`, `/tech/tasks/:id` | مهام اليوم والقادمة، الاتصال بالعميل، بدء التنفيذ، صور قبل/بعد من الكاميرا، قطع الغيار، بانتظار قطع، إرسال التقرير |
| الإشعارات | `/notifications` | مركز إشعارات لكل الأدوار + عدّاد غير المقروء |

العربية (RTL) هي الافتراضية مع تبديل فوري للإنجليزية، والتصميم متجاوب بالكامل (شريط تنقل سفلي للمالك والفني على الجوال).

## الأمان — الصلاحيات في قاعدة البيانات وليس في الواجهة فقط

- **Row Level Security** على كل الجداول: المالك لا يرى إلا وحداته وبلاغاته، والفني لا يرى إلا مهامه، وبيانات المالك تختفي عن الفني بعد إغلاق المهمة.
- **حالة الطلب لا تتغير بتحديث مباشر** — عمود `status` محجوب بصلاحيات الأعمدة، والتغيير يتم فقط عبر دوال `SECURITY DEFINER` تتحقق من الدور ومن صحة الانتقال (`transition_request`, `assign_request`, `tech_submit_work`, `review_work`...).
- الدور يُقرأ من `app_metadata` (لا يستطيع المستخدم تعديله) — محاولة رفع الصلاحية من التسجيل أو تعديل الملف الشخصي تُرفض.
- المرفقات في Storage خاصة، والوصول بروابط موقّعة لمدة ساعة، ومسار كل ملف مرتبط برقم البلاغ وتحميه سياسة RLS.
- مفتاح `service_role` يُستخدم فقط في الخادم لإنشاء الحسابات وبعد التحقق من أن المستدعي مدير.

اختبار آلي يشغّل الـ migrations على PostgreSQL حقيقي (PGlite) ويحاول 20 عملية اختراق/تجاوز:

```bash
npm run test:db
```

## التشغيل

### 1) مشروع Supabase
1. أنشئ مشروعًا جديدًا على [supabase.com](https://supabase.com) (يُفضّل منطقة قريبة).
2. شغّل ملفات `supabase/migrations/` **بالترتيب** من SQL Editor، أو عبر CLI: `supabase link` ثم `supabase db push`.
3. **Authentication → Providers → Email:** أوقف خيار *Allow new users to sign up* (الحسابات تنشئها الشركة فقط).
   ثم (اختياري) شغّل `supabase/seed/ola-projects.sql` لإضافة مشاريع الشركة الحالية (عُلا 17 حتى 25) بصورها وحالتها.
4. **Authentication → URL Configuration:** ضع رابط الموقع في *Site URL*، وأضف `https://YOUR-DOMAIN/auth/callback` في *Redirect URLs*.

### 2) المتغيرات
```bash
cp .env.example .env.local   # ثم عبّئ القيم من Settings → API
```

### 3) التثبيت والتشغيل
```bash
npm install
npm run create-admin -- admin@company.sa "اسم المدير"   # أول حساب إدارة
npm run dev
```

### 4) بيانات تجريبية (اختياري — للعرض فقط)
```bash
DEMO_SEED=yes npm run seed:demo          # مشروعان، 22 وحدة، 8 عملاء، 5 فنيين، 28 بلاغًا بمراحل مختلفة
DEMO_SEED=yes npm run seed:demo -- --purge   # حذف كل البيانات التجريبية
```
البيانات التجريبية مفصولة: لا تعمل بدون `DEMO_SEED=yes`، وكل حساباتها على النطاق `@demo.example.com`، ومشاريعها موسومة `[DEMO]`، ويُنصح بتشغيلها على مشروع Supabase منفصل للتجربة. كلمة المرور الافتراضية: `Demo@12345`.

| الدور | البريد |
|---|---|
| إدارة الشركة | `admin@demo.example.com` |
| موظف الصيانة | `supervisor@demo.example.com` |
| فني | `tech.ahmed@demo.example.com` |
| مالك | `owner1@demo.example.com` |

### 5) النشر
مناسب لـ Vercel مباشرة: اربط المستودع، أضف المتغيرات الأربعة، وانشر.

## هيكل قاعدة البيانات

`roles` · `profiles` (Users) · `company_settings` · `projects` · `buildings` · `units` · `owners` · `warranties` · `maintenance_requests` · `work_orders` · `work_order_parts` · `technicians` · `contractors` · `appointments` · `attachments` · `request_notes` · `quotes` · `notifications` · `notification_outbox` · `ratings` · `activity_logs` + العرض `request_overview` ودالة التقارير `report_summary`.

### دورة الطلب
`طلب جديد → قيد المراجعة → تمت الموافقة → تم تعيين الفني → تمت جدولة الزيارة → جاري التنفيذ → بانتظار اعتماد الإنجاز → مكتمل`
مع الحالات الجانبية: `بانتظار قطع غيار` · `مؤجل` · `مرفوض (بسبب إلزامي)` · `أعيد فتح الطلب`.
كل تغيير يُسجَّل في `activity_logs` باسم المنفّذ ودوره ووقته وملاحظته، ويولّد الإشعارات المناسبة تلقائيًا (Triggers).

### الضمان
عند إنشاء البلاغ يبحث النظام عن ضمان سارٍ للوحدة يغطي نوع العطل ويحفظ النتيجة (ضمن/خارج/غير محدد) مع السبب. موظف الصيانة يراجعها ويمكنه تعديلها، وإذا كان الطلب خارج الضمان يصدر عرض سعر (شامل الضريبة) ولا يمكن تعيين فني حتى يرد العميل.

### WhatsApp / SMS / البريد لاحقًا
كل إشعار يُضاف تلقائيًا إلى `notification_outbox` لكل قناة مفعّلة في الإعدادات. يكفي لاحقًا كتابة Worker (مثل Supabase Edge Function مجدولة) يقرأ السجلات `pending` ويرسلها عبر المزوّد ثم يحدّث حالتها.

## ملاحظات للمرحلة القادمة
- الدخول برقم الجوال (OTP) يحتاج ربط مزوّد SMS في Supabase Auth.
- تصدير PDF يتم من نافذة الطباعة في المتصفح («حفظ كـ PDF») للحفاظ على تشكيل العربية واتجاه RTL.
- التطبيق جاهز للتحويل إلى PWA أو تطبيق جوال (Capacitor/React Native) لأن كل المنطق في قاعدة البيانات وواجهات RPC.

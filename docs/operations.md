# التشغيل والموثوقية

## 1) الفحص التلقائي قبل النشر (GitHub Actions → CI)
كل تعديل يُرفع على `main` يشغّل: فحص الأنواع (TypeScript)، اختبارات قاعدة البيانات (كل الـ migrations + الصلاحيات + سير العمل)، وبناء المشروع.
- ✓ أخضر بجانب الـ commit = سليم.
- ✗ أحمر = فيه مشكلة؛ افتح Actions وشوف السبب. Vercel نفسه يرفض نشر بناء فاشل ويبقي النسخة السابقة شغالة.

## 2) مراقبة الأخطاء
- أي خطأ في صفحة (عند المستخدم أو في الخادم) يُسجَّل في جدول `error_events` ويظهر في **الإدارة → صحة النظام**.
- يوصل المدير إشعار عند ظهور نوع خطأ جديد (مرة بالساعة كحد أقصى).
- نفس الصفحة تعرض المهام المجدولة وآخر تشغيل لكل وحدة، والرسائل المعلّقة/الفاشلة.

## 3) المهام المجدولة (pg_cron داخل Supabase)
| المهمة | التوقيت (الرياض) |
|---|---|
| تصعيد البلاغات المتأخرة/الواقفة | كل ساعة (د 15) |
| تصعيد طلبات الموظفين المعلقة > يومين | كل ساعتين |
| تنبيهات الحضور (غياب بدون طلب / تأخير متكرر) | الأحد–الخميس 10:30 |
| تذكير متابعة العملاء المحتملين | يوميًا 8:00 |
مهمة Vercel اليومية (`/api/cron/daily`) تشغّل تنبيهات الضمان والحذف حسب مدد الاحتفاظ وتعيد إرسال الرسائل، وتشغّل المهام أعلاه احتياطيًا — تحتاج `CRON_SECRET` في Vercel.

## 4) النسخ الاحتياطي
- **يومي ومشفّر عبر GitHub** (`.github/workflows/backup.yml`) — يحفظ 30 يومًا.
  أضف سرّين في GitHub → Settings → Secrets and variables → Actions:
  - `SUPABASE_DB_URL`: من Supabase → زر **Connect** → **Session pooler** (مو Direct — GitHub ما يدعم IPv6).
  - `BACKUP_PASSPHRASE`: عبارة سر طويلة، احفظها في مكان آمن (بدونها ما ينفتح الملف).
  جرّبه: Actions → Daily database backup → Run workflow.
- **الاسترجاع:** `gpg -d db-YYYY-MM-DD.dump.gpg > db.dump` ثم `pg_restore --no-owner -d "<رابط القاعدة>" db.dump`.
- **خطة Supabase Pro** تضيف نسخًا يومية تلقائية مع استرجاع بنقرة (موصى بها عند الإطلاق).
- الملفات المرفوعة في Storage غير مشمولة في dump القاعدة.

## 5) فصل بيئة التجربة عن الحقيقية
1. أنشئ مشروع Supabase ثاني باسم `ola-staging` (الخطة المجانية تسمح بمشروعين).
2. شغّل عليه كل ملفات `supabase/migrations` بالترتيب، ثم بيانات التجربة (`seed/`).
3. في Vercel → Settings → Environment Variables: خلّ قيم **Preview** تشير لمشروع التجربة، و **Production** للمشروع الحقيقي.
4. أي فرع غير `main` يُنشر كنسخة تجربة تلقائيًا على مشروع التجربة.
5. قبل الإطلاق: شغّل `demo-purge.sql` على المشروع الحقيقي.
